# 215. Kth Largest Element in an Array

## Thought process

1. Brute force: sort descending, take index `k-1` — O(n log n).
2. The problem explicitly asks for better than O(n log n) — so a full sort is off the table.
3. Key insight: you don't need the full order among the top k, just the identity of the kth-largest. So track only the **current top-k candidates**, not the whole array's order.
4. Keep a **min-heap of size k**. `heap[0]` is always the *weakest* member of the current top-k.
5. Seed the heap with the first k elements and `heapify`.
6. For every remaining element: if it beats the current weakest (`heap[0]`), swap it in via `heapreplace` (pop the weakest, push the new one, in one O(log k) step).
7. After processing everything, `heap[0]` is exactly the kth largest.

## Why a min-heap (not a max-heap)

You need fast access to the *weakest* member of your current top-k, so you can decide whether a new number deserves to displace it. A min-heap gives O(1) access to that weakest member (`heap[0]`) and O(log k) to swap it out — a max-heap would give you the *strongest* member instead, which isn't what the decision needs.

## Complexity

- Time: O(n log k)
- Space: O(k)

## Common pitfall

Building a heap of all `n` elements (or building a max-heap of everything) instead of a size-**k** min-heap — that loses the "better than O(n log n)" property the follow-up is specifically asking for.

## Cold-review self-check

- Why min-heap and not max-heap, given the goal is finding the *largest* values?
- At any point mid-loop, what does `heap[0]` represent?
- What's the time complexity, and specifically why is keeping the heap at size k the thing that makes it better than sorting?
