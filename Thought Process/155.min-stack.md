# 155. Min Stack

## Thought process

1. Requirement: push/pop/top/**getMin** must all be O(1). Ruling out "call `min()` over the stack every time" — that's O(n).
2. Idea: keep a second, parallel stack (`min_stack`) that always tracks "the minimum so far, as of this point in the main stack's history."
3. **Push:** always push to the main stack. Push to `min_stack` too, but only if the new value is `<=` the current min — that keeps `min_stack`'s top equal to the overall current minimum.
4. **Pop:** if the value being popped equals `min_stack`'s top, pop `min_stack` too — that minimum's "reign" is over now that its value is leaving the main stack.
5. **getMin:** just `min_stack[-1]` — O(1) by construction, no scanning required.

## Why two stacks

The minimum changes over time as values get pushed and popped, and a stack's LIFO nature is exactly what lets you cheaply "undo" the min back to whatever it was before — as long as `min_stack` is kept in lockstep with the same push/pop rhythm as the main stack.

## Complexity

- Time: O(1) for every operation
- Space: O(n) worst case (every pushed value is a new minimum)

## Common pitfall

Using `<` instead of `<=` when deciding whether to push to `min_stack`. With strict `<`, a **duplicate** of the current min never gets pushed again — so later, popping the "real" copy off `min_stack` would drop the tracked min past a value that's still logically sitting in the main stack.

## Cold-review self-check

- Why does the min_stack push condition need to be `<=`, not `<`?
- What specifically triggers a pop from `min_stack` (not just any pop from the main stack)?
- Why can't you track "the min" as a single plain variable instead of a whole second stack?
